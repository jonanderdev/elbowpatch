# 19. How a PDF is made: the pages, the fonts and the library

Date: 2026-11-07 · Status: accepted

The reasons for making the file in the app are in 0007. This records how, and what was tried.

## The browser sets the lines; the app writes the file
- The text is laid out off screen by the browser, in CSS columns one printed page tall, at **8 times** the printed size and divided again. WebKit rounds the boxes it reports to whole pixels, so at 1x a word could be 1 px out; at 8x the same. Every browser takes this one path.
- The layout takes nothing from the screen, the text settings or the theme: its own column (117 mm), body 11 pt, leading 1.55, titles 2.05 times, paper colours. Only the writer's *indent* and *drop cap* settings enter, because they are how the writer sets their own text. A drop cap is a floated first letter, the same in every browser, since not all have `initial-letter`.
- Each word is read back with a `Range`, a line at a time; a word split by a hyphen or at the column's edge is read letter by letter. The hyphen is not in the DOM, so it is found where the browser left it: a box of its own (Chromium) or room in the word's box (Firefox, WebKit). Each word is then placed where the browser put it, in a real run of glyphs with a real space between words, so the text can be selected and searched. Kerning, which `pdf-lib` leaves out, is put back with the numbers of a `TJ` array. A baseline is found once for each style by a probe, since browsers measure a text box from different font metrics.
- **The same pages hold within one browser, not across browsers.** Hyphenation differs by engine and operating system, so a piece exported from Safari on a phone and from Chrome on a Mac can break its lines, and so its pages, differently. Doing the hyphenation ourselves, with a pattern file for each language, would make them equal; it was left for when it is missed.
- **The text keeps the page's marks, and its own language.** Bold is Literata at 600, italic is EB Garamond italic at 1.17 times, a pull quote is that italic at 1.36 times, centred, and Markdown the page keeps as written is set as a paragraph of its own words, symbols and all. The piece's language is the `lang` of the off-screen text, so each browser hyphenates by it, as it would on screen if the writer justified. The drop cap is upright Literata at 600 whatever mark the first word carries (the design says upright; the page's own cap would take an italic's face there). It stands on a first paragraph that was kept as written too, and a paragraph after one steps in like any other, as the page does.
- Letter-spacing switches ligatures off in a browser, and the title has some; the title is drawn without them, as the browser measured it.
- The paragraph space is one line of the leading, as the Ready frames of the printed pages show (DESIGN.md says "the screen's paragraph space", which on screen is one em; the frames win).
- Optical size is in CSS px, as the browser sets it, in the layout and in the fixed fonts alike: 11 pt is `opsz` 14.667.

## Fonts
- `pdf-lib` and fontkit cannot embed the shipped `woff2` (fontkit cannot vary a `woff2`), and embed only a variable font's default weight. So **fixed files** are made at build time (`scripts/pdf-fonts.mjs`, which needs Python and fonttools once, and is run by hand; its output is committed): Literata at 300 (title), 360 (text), 600 (bold, drop cap) and italic 400 (running head), and EB Garamond italic at 400 and 600, from the same versions as the web fonts (Literata 3.103, EB Garamond 1.003).
- Latin, extended Latin and Vietnamese are in **one file** per face. A word such as `Łódź` or `Việt` needs glyphs that the web fonts keep in three files; from one file, it sets.
- The files are fetched when the first PDF is made, not installed (0011 is amended).
- **No character goes missing.** Each face also has a Cyrillic file (the web fonts' Cyrillic and its extension) and a Greek file (Greek and its extension), 37 to 80 KB each, which also hold the punctuation, digits and space that stand among their letters, so a Russian or Greek sentence is one run in one file. The Latin file keeps its name; the others add `-cyrillic` or `-greek`. A list made with the files (`coverage.json`, from each file's own character map, not from the web fonts' ranges) says which file holds what, so no font is fetched to find out, and a piece fetches only the files its characters need: a piece in English never fetches Cyrillic or Greek. The list is per face, because EB Garamond lacks some characters Literata has.
- Each word is cut into runs a letter at a time (a letter with its marks, an emoji with its joiners, count as one), each run as long as one file can hold. Kerning across the seam between two files is lost; nothing else is. Decomposed letters are written as the precomposed ones the file holds. A letter whose marks have no precomposed form would sit in the wrong place (a `TJ` only moves the pen sideways), so it is drawn as an image, like the characters below.
- **What no file holds** (an emoji, Arabic, Japanese, Hebrew, Thai) is drawn by the browser on a canvas, at three times the printed size, in the same face and ink the line has, and placed as an image on the baseline where the word stands. The word keeps the place the browser gave it, so the lines around it do not move; the run itself goes on from the pen by the width the browser measures. An image cannot be selected as text; that is accepted. Images are made from the pixels directly (colour and a soft edge as two Flate streams), not as PNG, because `embedPng` decodes and encodes the picture again, which is slow on a phone; each is made once for a face, size, colour and text. A word of such characters is not hyphenated.
- The running head, which the browser does not lay out, is set the same way, and shortened a letter at a time, never through a pair of surrogates.

## The library
- `pdf-lib` 1.17.1 and `@pdf-lib/fontkit` 1.1.1 (MIT, with `pako`, MIT and Zlib, which `pdf-lib` uses), about 510 KB gzipped with the app's own PDF code. Their last releases are from 2022; they run in current Chromium, WebKit and Firefox. They are the only pair that writes real text with embedded subset fonts in the browser; a smaller route (drawing each page as an image) would make a file that cannot be searched. The code is one lazy chunk named `pdf`, left out of the install, so a writer who never makes a PDF pays nothing, and the main bundle did not grow.
- `pdfjs-dist` (Apache-2.0) reads the file back in the tests only; it is a development dependency and never in the app.

## Out of the install, kept after the first PDF
- The code and the fixed fonts are left out of the precache by name (`globIgnores` for the `pdf` chunk, and the `.ttf` files are outside the glob). One cache-first rule in the service worker keeps them the first time they are fetched; their names carry a hash, so a kept file is never stale, and a new version asks for new names.
- The `pdf` chunk takes only the PDF modules and the libraries (`includeDependenciesRecursively: false`). With the default, code the whole app shares, such as the Markdown reading, was pulled into it, the main file then needed it to start, and the app stopped opening offline. A test now opens the app offline, so that cannot come back unseen.
- A PDF asks the network only for those files: plain GETs of the app's own assets, nothing sent. The offline test records the requests and checks it.
- Offline before the first PDF, the row says so (`navigator.onLine` is false when the fetch fails); any other failure shows the failure line. Both are in the row's status, so a screen reader hears them.
- There is no `clientsClaim` (0010), so a first session is not held by the service worker: a PDF made in it is fetched but kept only from the next load. Writers reload long before they need it offline, and the browser's own cache usually holds it; left as it is.

## Known, and left
- A retry after a failed first load works in Chromium and Firefox; WebKit remembers a module that failed until the page is loaded again.
