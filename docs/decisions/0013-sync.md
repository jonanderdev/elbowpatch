# 13. Sync: what we know before building it

Date: 2026-11-04 · Status: proposed

Sync comes after daily use has proved the app (docs/brief.md). These are the ideas so far, moved here from the old project notes. They get challenged when sync is planned.

## Decision

### One place at a time
- v1 of sync ships one provider: the writer's own private GitHub repo, which the app creates for them. Writers never make or configure a repo by hand.
- Connecting another place replaces the current one after one confirmation. The old place stops receiving copies and keeps what it has. There is no dormant second connection.
- Each piece's place in the text travels with it, so another device opens where the writer was. The most recent wins.
- Other providers (other Git hosts, WebDAV, S3-compatible storage) are future work and a good area for contributions.

### A narrow provider contract
- The editor and the Time Machine know nothing about any provider. A provider implements something like `authenticate()`, `listPieces()`, `readPiece(id)`, `writePiece(id, content, message)`, `listVersions(id)` and `readVersion(id, versionId)`.
- Each provider declares whether it keeps history. A Git-based one pushes the current section files, and its commits are the far history. Others also push a `history/` folder of the thinned versions.
- It pushes every few minutes while writing, and on pause and close, to stay within rate limits.
- The Time Machine shows local versions offline, and fills in older moments from the provider online.
- One writer at a time is assumed. A conflict is last-write-wins, plus keeping both as a draft. Content is never silently discarded.
- Sync runs in the background, never blocks the editor, and is safe to retry.

### GitHub
- Use the REST API, because the git protocol does not allow browser CORS.
- The OAuth code exchange needs a client secret, so it needs a tiny stateless function that stores and logs nothing. Open question: the README says the app has no server of its own, so this has to be squared with that promise.
- For technical users, the fallback is pasting a fine-grained personal access token.
- Self-hosters register their own OAuth app and deploy their own function. This must be documented clearly.

## Consequences
- Safari on iOS lacks the File System Access API, so sync is network-based, not folder-based.
- Installed iOS apps have no background sync, so sync runs while the app is open.
- History is never stored in a raw `.git` directory in a cloud-synced folder.
